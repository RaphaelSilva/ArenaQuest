## 1. Objectives

- **One widget registry drives the dashboard.** Every widget type — config schema, version, `migrate`, `multiple`, allowed scopes and data schema — lives in `packages/shared/domain/dashboard/`, read by the API, the web and the deploy preflight (RFC §1).
- **Today's dashboard becomes eight widgets with no visual regression and one API call.** Level, streak, ranking, daily quests, missions, weekly challenges, badges and the roots-only roadmap render from `layout` + `widgets`; ranking and roadmap data move server-side, replacing the web's four parallel calls (RFC §4, §8).
- **A student owns a layout.** Show/hide, reorder and configure instances — several of the same type where allowed — in Settings → Dashboard, stored server-side as a strict, versioned JSON document (RFC §2, D1–D4, D23).
- **Defaults per label and per group, resolved deterministically.** Code → label (profile, shipped with the deploy) → group (backoffice, highest priority wins) → student copy, with a "new default" notice, restore and admin-locked widgets (RFC §3, D5–D7, D14, D17, D18).
- **A roadmap rooted at any topic.** Direct children of a start topic as stages, leaf-based progress computed on the server, and an unavailable state that reveals nothing (RFC §5, D8, D10).
- **Continue where you left off.** The last visited topic, from a new `topic_progress.last_visited_at` stamped on every visit, completed topics included (RFC §6, D19).
- **Instructor recommendations as a live widget.** Up to 10 `{ topicId, reason }` items authored in a group default, filtered by access per student, read live even by students with a copy (RFC §7, D13, D20).
- **The aggregate stays fast and resilient.** Data only for enabled instances, a failure boundary per widget, and a p95 target fixed from a measured baseline (RFC §4, D15, D22).
- **Full i18n coverage** across `dict-en` / `dict-pt`, enforced by `check-i18n-coverage.js`.

Out of scope (explicit, from RFC 0008 Non-Goals):
- **Free grid / separate mobile layout** — same order in a single column on mobile (D2, D24).
- **Algorithmic or behavioural recommendations; recommendations that grant access, enroll or create progress** — a recommendation is guidance only.
- **Media resume position** — "continue" is topic-level; RFC 0023 may refine the signal later.
- **Manual badge approval, badge engine / catalog / progression changes** — delivered by M7, M15, M16.
- **Per-language recommendation text** — a single tenant string (D20).
- **Ranking display names and the `'en-US'` greeting date** — backlog items, independent of this milestone.
- **Notifications, widget analytics, widgets on other pages.**
- **Backlog `user-experience/10`** — a prerequisite of the continue widget's quality, delivered separately.

## 2. Functional Requirements

**Registry and layout document**
- `WidgetType` = `level | streak | ranking | daily_quests | missions | weekly_challenges | badges | roadmap | continue | recommendations`. Each definition declares `version`, a **strict** `configSchema` (unknown keys rejected), a pure `migrate(fromVersion, raw)`, `multiple`, `scopes` and a data schema.
- Configs: the seven current non-roadmap types take `{}`; `roadmap` takes `{ startTopicId: string | null }` (`null` = roots, `multiple: true`); `continue` takes `{}`; `recommendations` takes `{ title?: string, items: { topicId, reason }[] }` (`multiple: true`, `group` scope only).
- A layout is `{ widgets: WidgetInstance[] }`, each instance `{ id (uuid), type, version, config, locked? }`; array order is render order.
- Limits in `domain/dashboard/limits.ts`: **12 instances per layout**, **10 items per recommendations widget**, **reason 1–280 characters after trim**; duplicate `topicId` within one recommendations instance rejected.
- **Read is tolerant:** each instance is migrated to its current version and validated; an unknown type or invalid config drops that instance only, logging `{ instanceId, type }`. **Write is strict:** the whole document must validate or the request is `400` with the failing path.

**Resolution**
- Tiers: code default (`default-layout.ts`, today's arrangement) → label default (`DASHBOARD_DEFAULT_LAYOUT`) → group default → student copy.
- Label default: absent var → code default; present but invalid → code default plus an error log; never a `500`.
- Group default: among the student's groups that have one, the highest `priority` wins; ties break by `group_id` ascending; no merging.
- Student copy: created on the first `PUT`, storing `based_on` (`code` | `label` | `group:<id>`) and that default's `updated_at`. `layoutSource.newDefault = true` when the default that applies now differs from `based_on` or is newer than the stored timestamp. `DELETE` removes the copy (restore default).
- Locks: a `locked: true` instance of the applicable default must remain in the copy — a `PUT` removing it is `409 WIDGET_LOCKED`; moving it is allowed; a locked instance added to the default later is appended to the copy on read until the student saves.
- Recommendations in a student copy keep only their instance `id`; their `items` are read from the group default that applies now; no matching instance → the widget renders nothing.

**API**
- `GET /v1/me/dashboard` → `{ layout, layoutSource: { kind, groupId?, newDefault }, widgets: Record<instanceId, WidgetData | null> }`; data computed only for enabled instances, in parallel, each in its own failure boundary (`null` on failure); `Cache-Control: private, max-age=15`; every field has a real Zod/OpenAPI schema (no `z.any()`).
- `GET | PUT | DELETE /v1/me/dashboard/layout` — effective layout, source, `newDefault` and the addable types; save; restore. `Cache-Control: private, no-store`. `PUT` and `DELETE` return the new effective layout.
- `GET /v1/admin/groups/{groupId}/dashboard-layout` (`admin`, `content_creator`; `404` when none); `PUT` (body `{ priority, layout }`) and `DELETE` (`admin` only, `403` for `content_creator`). Recommendation `topicId`s must exist and not be archived on write (`400` otherwise).
- `GET /v1/admin/dashboard/label-default` (`admin`, `content_creator`) — the deployed label default, or the code default with `source: 'code'`.

**Widgets**
- Current eight: same data and look as today; the roadmap default (`startTopicId: null`) shows the accessible roots, now with leaf-based progress.
- Roadmap: stages = accessible direct children of the start topic (or roots) in `sort_order`; percentage = completed accessible leaves ÷ accessible leaves of the stage subtree (a leaf stage is 0 or 100); status `completed` at 100, `in_progress` when > 0 or any subtree node has progress, else `not_started`. Start topic archived, unpublished, deleted or inaccessible → `{ unavailable: true }` with no id or title; config preserved.
- Continue: the accessible, published, non-archived topic with the latest `last_visited_at` → `{ topicId, title, status }`; none → empty state linking to the catalog.
- Recommendations: items whose topic is not accessible, unpublished or archived are omitted with no placeholder; order as authored.

**Visits**
- `topic_progress.last_visited_at` (nullable) is stamped by every successful `POST /v1/me/topics/{id}/visit`, **including on a completed topic**; the status never moves backwards and the existing early return still skips the status upsert.

**Label profile and deploy**
- `config/labels/<label>.jsonc` may declare `dashboard.defaultLayout`. The deploy preflight validates it with the shared schema (via `apps/api/scripts/check-dashboard-layout.ts`) and checks its serialised size; an invalid layout aborts the deploy before any command. A valid one is passed as `wrangler deploy --var DASHBOARD_DEFAULT_LAYOUT:<json>` (Worker deploy and Workers Preview alike).

**Web**
- `DashboardContent` renders `layout` through a `type → component` map; two columns on `lg`, one on mobile, same order; one `GET /v1/me/dashboard`.
- Settings → Dashboard: list with show/hide, move up/down, configure (roadmap topic picker), add from addable types, lock icon, "new default" notice, **Restore default**; error states for `400` / `409`.
- Admin → Groups → `[groupId]` → Dashboard: the same editor at group scope plus `priority`, lock toggles and the recommendations editor (topic picker, reason with counter, order); read-only for `content_creator`; a read-only preview of the label default.
- Every new string in both dictionaries; `check-i18n-coverage.js` green.

## 3. Acceptance Criteria

- [ ] With no label, group or student layout, `/dashboard` renders today's eight blocks in today's order from exactly **one** network call to the API (web test asserts a single `GET /me/dashboard`; the leaderboard, `/topics` and `/me/progress/topics` calls are gone from `dashboard-api.ts`).
- [ ] `openapi.json` has no `z.any()`-derived `{}` schema under `GET /v1/me/dashboard`; `api-types.gen.ts` types every widget's data.
- [ ] Shared specs: every registry type round-trips its default config; `migrate` is pure; a 13-instance layout, an unknown type and an unknown config key each fail strict parsing; the tolerant reader drops exactly the bad instance.
- [ ] API: `PUT /v1/me/dashboard/layout` with an invalid document is `400` and writes no row; a valid one is returned by the next `GET` and by `GET /v1/me/dashboard`; `DELETE` restores the default.
- [ ] API: a student in groups A (`priority` 10) and B (`priority` 20) gets B's default; with equal priorities the lower `group_id` wins.
- [ ] API: after B's default is updated, a student with a copy based on B gets `newDefault: true`; after `DELETE` they get B's new layout and `newDefault: false`.
- [ ] API: removing a locked instance is `409 WIDGET_LOCKED`; moving it is `200`; a locked instance added to the default later appears in the copy on read.
- [ ] API: `content_creator` gets `200` on the admin `GET`s and `403` on `PUT`/`DELETE`; a student gets `403` on every admin route.
- [ ] API: an invalid `DASHBOARD_DEFAULT_LAYOUT` yields the code default (no `500`) and one error log line; an absent var yields the code default.
- [ ] API: roadmap rooted at T returns T's accessible children with leaf-based percentages on a fixture tree; archiving T, unpublishing it or revoking access returns `{ unavailable: true }` with no title or id; restoring access restores the stages.
- [ ] API: visiting a completed topic sets its `last_visited_at`, keeps `status = 'completed'`, and makes it the continue widget's topic.
- [ ] API: a recommendations widget with accessible X and inaccessible Y returns only X with its reason; editing the group default changes the result for a student with a copy on the next uncached read.
- [ ] API: a widget whose data source throws returns `null` for that instance while the other instances return data.
- [ ] Deploy: `scripts/deploy` tests cover a profile with an invalid `dashboard.defaultLayout` (preflight fails, no command runs), a valid one (`--var DASHBOARD_DEFAULT_LAYOUT:` present on the Worker deploy and preview commands) and none (no `--var`).
- [ ] Web: Settings → Dashboard hides, moves, configures and restores, and shows the `409` and "new default" states; Admin → Groups → Dashboard is read-only for `content_creator`.
- [ ] Performance: the Phase 1 baseline p95 of `GET /v1/me/dashboard` on the demo seed and the agreed target are recorded in this milestone's §6; the final aggregate meets the target.
- [ ] `make lint`, `make test-api`, `make test-web` and `node --test 'scripts/deploy/**/*.test.mjs' 'scripts/cloudflare/**/*.test.mjs'` pass; `check-i18n-coverage.js` passes with identical EN/PT keys.
- [ ] No diff outside the scope declared in the guardrail.

## 4. Specific Stack

- **Backend:** Cloudflare Workers + Hono; per-request adapters built in `buildApp(env)`; a new `dashboard` container group (`dashboardLayoutRepo`, layout resolver); controllers return `ControllerResult<T>` from `src/core/result.ts`. **Validation is `@hono/zod-openapi` `createRoute` + Zod at the route layer — not `@ValidateBody`/`@Body` decorators**; the layout body is parsed again by the shared strict schema in the controller. Admin writes add `requireRole(ROLES.ADMIN)` in their own chain (the `/admin/*` umbrella keeps admitting `content_creator` for reads). Roadmap progress is one recursive CTE over `topic_nodes` restricted to the effective access set and joined to `topic_progress`. Layout documents are `TEXT` JSON columns. `openapi.json` regenerated with `pnpm dump-openapi`.
- **Shared:** new `packages/shared/domain/dashboard/` (registry, `layout.ts`, `limits.ts`, `default-layout.ts`, `resolve.ts`, per-widget data schemas); `types/dashboard.ts` reshaped to `DashboardResponse`; new `IDashboardLayoutRepository` port. Zod only — no new dependency.
- **Deploy:** `scripts/deploy/core.mjs` plans a fail-closed step and `scripts/cloudflare/deploy.mjs` maps it to `pnpm --filter api exec tsx scripts/check-dashboard-layout.ts` (same mechanism as the `check-no-dev-seed.ts` guard) on the profile's `dashboard.defaultLayout`; `scripts/cloudflare/deploy.mjs` appends `--var DASHBOARD_DEFAULT_LAYOUT:<json>` to `wrangler deploy` and `wrangler preview`.
- **Frontend:** Next.js 15 App Router, React 19, Tailwind CSS v4; client components with `useDict()`; the topic picker reused from `components/missions/SingleTopicPicker.tsx`; both i18n dictionaries; `check-i18n-coverage.js`.
- **Tests:** Vitest (shared specs for registry, migration, resolution, limits); Vitest + `@cloudflare/vitest-pool-workers` (API — resolution tiers, priorities, locks, `newDefault`, role matrix, roadmap subtree and leak cases, `last_visited_at`, per-widget failure, label env fallback); `node --test` (deploy preflight and `--var`); Vitest + RTL (web — widget host, Settings editor, admin editor, single-call dashboard).

## 6. Decisions recorded (from RFC 0008 "Resolved Decisions")

Decided by the product owner on 2026-10-12 (RFC 0008 D1–D24), plus the implementation choices this milestone pins.

1. **Admin defaults, student adjusts in Settings** (D1) — the dashboard is neither fixed nor fully admin-controlled.
2. **Toggle, order and per-widget config; no free grid** (D2) — rules out drag/resize and absolute positions.
3. **Layout = list of instances; repeated types allowed where the registry says `multiple`** (D3) — two roadmaps rooted at different topics are valid.
4. **Server-side JSON document validated by a shared Zod schema** (D4) — no `localStorage`, no normalised widget table.
5. **Defaults per label and per group; group overrides label** (D5).
6. **Highest explicit group priority wins; tie → lower `group_id`** (D6) — no merging of group layouts.
7. **Customising creates a copy; notice + restore on default change** (D7) — a default change never rewrites a student's copy.
8. **Roadmap = direct children of the start topic, leaf-based progress, server-side** (D8) — retires the client-side 0/50/100 adapter.
9. **Version 1 ships the eight current widgets plus roadmap, continue and recommendations** (D9).
10. **Unavailable start topic → empty state without title; config kept** (D10).
11. **Admin writes defaults; `content_creator` reads** (D11) — M27 precedent.
12. **RFC 0008 rewritten in place, history kept** (D12).
13. **Recommendations are a live widget inside the group default; no own table; the student hides, never edits** (D13).
14. **Admin can lock a widget: movable, not removable** (D14) — `409 WIDGET_LOCKED`.
15. **One aggregated `GET /v1/me/dashboard`, enabled widgets only, per-widget degradation** (D15).
16. **One milestone in three phases** (D16).
17. **Label default in `config/labels/<label>.jsonc`, shipped with the deploy** (D17) — changes go through a PR.
18. **Invalid label default blocks the deploy; runtime falls back to the code default with a log** (D18) — never a `500`.
19. **Continue = last visited topic via `topic_progress.last_visited_at`** (D19) — needed because a visit to a completed topic touches nothing today.
20. **Recommendation reason is one tenant string, untranslated** (D20).
21. **Limits 12 / 10 / 280** (D21) — in `domain/dashboard/limits.ts`, the single source of truth.
22. **p95 target fixed after measuring the baseline in Phase 1** (D22) — baseline and target are written here when measured.
23. **Per-instance `version`, migration on read, invalid instance dropped with a log** (D23).
24. **Mobile: same order, single column** (D24).
25. **Inaccessible recommendation items are omitted, not redacted** — unlike mission steps, a suggestion is optional; an omitted item reveals nothing (RFC §7).
26. **The preflight validates through a TypeScript check script, like `check-no-dev-seed.ts`** — `scripts/deploy/core.mjs` is plain Node and cannot import the shared Zod schema directly; one schema, one validator.
27. **Migrations `0033` (layouts) and `0034` (`last_visited_at`)** — renumbered if another migration lands first; `dashboard_group_layouts.group_id` cascades on group delete, `dashboard_user_layouts.user_id` on user delete.
28. **Open, non-blocking:** whether the group editor lives on the group detail page (planned here) or on a dedicated defaults page — UX detail with no contract impact; revisit in the frontend task.
