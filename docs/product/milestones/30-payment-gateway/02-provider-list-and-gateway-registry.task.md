# Task 02 — Backend: Provider list, gateway registry and stub adapter (Phase 0)

**Status:** ✅ Done
**Milestone:** [30 — Payment Gateway](./milestone.md)
**RFC:** [RFC 0026](../../RFCs/0026-payment-gateway-hosted-checkout-collection-for-invoices-and-.md)
**Team:** Backend API
**Depends On:** [Task 01](./01-payment-contracts.task.md)

## Summary

Turns the per-label, per-environment variable **`PAYMENTS_PROVIDERS`** into a checked value and a
**`GatewayRegistry`**: the parser applies the five rules of RFC §8.1, the registry resolves an
adapter by provider name, and the container exposes both on a new `payments` group. An invalid
list is a recorded state that makes the payment routes answer `500 PAYMENTS_CONFIG_INVALID` —
never a throw at container build and never a silent `none`. A programmable **stub adapter** for
tests ships with it, so every later task can drive the whole flow without a provider. After this
task the default (`none`) is observable: an empty registry, and nothing else in the Worker changes.

## Dependencies

- [Task 01](./01-payment-contracts.task.md) — hard code dependency: the port, the provider and
  method unions and the capability table the rules read.

## Technical Constraints

- **Scope guardrail:** changes restricted to:
  - `apps/api/src/core/payments/config.ts` (new) — the list parser, the key-mode assertion, the
    config result type.
  - `apps/api/src/core/payments/gateway-registry.ts` (new) — adapter lookup by provider name,
    `payOptions` derivation.
  - `apps/api/src/container.ts` — the `payments` group (registry and config result only; the
    repository and the service join in Tasks 03 and 06).
  - `apps/api/wrangler.jsonc` — `PAYMENTS_PROVIDERS` and `PAYMENTS_KEY_MODE` in the top-level
    `vars` and in every `env.*` block.
  - `apps/api/worker-configuration.d.ts` (regenerated by `make cf-typegen`), `apps/api/.dev.vars.example`.
  - `apps/api/test/adapters/payment/stub-gateway-adapter.ts` (new) — the test double.
  - `apps/api/test/core/payments/**` (new) — parser and registry specs.
- **Never a silent fallback.** The container never throws on a bad list: it holds either a valid
  configuration or an invalid one with its reason, and the routes of Tasks 06–09 translate the
  invalid state into `500 PAYMENTS_CONFIG_INVALID` (the `SUBMISSIONS_*` precedent in
  `src/core/submissions/config.ts`). An absent variable means `none`.
- **The registry is built per request** inside `buildContainer` — no adapter instance in module
  scope. It takes an **adapter-factory map** as a parameter: the production map is empty in this
  task (Task 05 registers `mercadopago`), so any list other than `none` is invalid until then;
  tests pass their own map to bind stubs under real provider names.
- **The stub never ships.** It lives under `apps/api/test/`, like
  `test/adapters/rate-limit/in-memory-rate-limiter.ts`, and no file under `src/` imports it
  (milestone §6, decision 21).
- **Key mode (milestone §6, decision 19).** `PAYMENTS_KEY_MODE` is `test` or `live`; absent means
  `test`. Every `*-staging` block and the top-level `vars` say `test`, every production block
  says `live`. The assertion compares that value with the mode each provider's secret key
  declares by its prefix, with no provider call. It never logs a key or any part of one.
- **Secrets.** `PAYMENTS_<PROVIDER>_SECRET_KEY` / `PAYMENTS_<PROVIDER>_WEBHOOK_SECRET` are read
  from the environment and handed to the adapter factory; this task writes none anywhere.

## Scope

**In:**
- The grammar of RFC §8.1 (`none`, `provider:method+method`, comma-separated entries, an entry
  with no method) and its five rules: a provider at most once and known, every method known; a
  method offered by at most one provider; every method in the provider's capability table for the
  active currency; both secrets present for every listed provider, including one with no method;
  an entry with no method keeps the provider bound and offers nothing.
- `GatewayRegistry`: `get(provider)`, `isEmpty`, and `payOptions` — the entries that offer at
  least one method, in list order.
- The key-mode assertion as a function of the configuration, callable by a route and by the
  reconcile run (Task 09).
- `PAYMENTS_PROVIDERS: "none"` everywhere in `wrangler.jsonc`; `PAYMENTS_KEY_MODE` as above; both
  documented in `.dev.vars.example`.
- The stub adapter: programmable payments, refunds and webhook verdicts, recording the calls it
  received, constructible under any provider name.
- Tests: every rule as a refusal with its own reason; whitespace and casing; `none` and absent;
  list order preserved in `payOptions`; a retired entry bound but not offered; a mode mismatch in
  both directions; two stubs bound under two provider names.

**Out:**
- The deployment schema, the `~=` operator and `infra-check` output (Task 15).
- The Mercado Pago adapter and its entry in the production factory map (Task 05).
- Any route, and `GatewayService` (Tasks 06–09).
